# 模型可用性：真实业务观察与渠道控制

入口：`/dashboard/monitor` 的「可用性监控」工作区，位于左侧「监控 → 模型检测」。原有检测功能保留在同页「检测工具」工作区。旧 `/dashboard/availability` 链接保留筛选并跳转到合并页面。当前整合已完成本地验证，尚未上线。

## 默认行为

默认仅观察。页面刷新只读取配置和已记录的结果，不发送模型活性测试、智商题或指纹请求，不修改原有检测计划。

检测配置可按中转站选择「仅业务观察」「手动测试」「允许定时检测」，未配置站点按仅观察处理。检测权限由后端执行，与可用性自动隔离设置独立。手动模式只允许点击后执行；定时模式还需原检测计划启用。

渠道行提供单次测试入口，弹窗展示指定账号、模型和计费提示，打开弹窗不发送推理请求。执行时只测试该账号一次，不换账号、不重试；结果单独保存，不改变业务观察、隔离、账号启停或发布选择。已隔离渠道可单次诊断，成功后仍需人工解除隔离。

状态按供应商、连接账号、上游模型分别记录。新功能启用前的日志不回放为自动隔离证据；没有请求或记录超过新鲜度时显示未验证，不判定模型失效。模型目录不是推理成功证据。

流式请求只采用最终状态，排除未完成占位记录、用户取消和内部测试。不能确认有效内容的空文本回复不记为成功，也不据此自动隔离，以免误伤工具调用。凭据、提示词和回答正文不进入可用性状态；仅保存计数、时间、脱敏错误摘要及关联请求 ID。

## 三个标签

- 渠道状态：筛选账号和模型、查看真实调用记录、人工隔离或解除隔离。
- 自动处理规则：观察/自动模式、允许自动处理的供应商、失败次数、时间窗口、默认冷却和记录新鲜度。
- 处理记录：最近 500 条规则变更、人工操作、自动隔离和恢复记录，关联已有请求日志。原始日志可能按原有保留策略清理。

## 隔离规则

只有显式开启自动模式且被勾选的供应商才会自动处理：

- 明确的无效凭据、余额不足：暂停对应账号，人工处理后解除。
- 上游明确拒绝模型：只暂停该账号的对应模型，需人工复核。
- 429：默认冷却 10 分钟，可配置。
- 上游超时、5xx、断流：默认 15 分钟内累计连续 3 次后冷却 10 分钟。
- 代理、DNS、连接、证书异常或无法分类的错误：记录异常，不批量隔离模型。

冷却结束仅恢复候选资格，先由一笔真实业务确认恢复；并发请求不能同时占用恢复资格。没有业务就继续待恢复。人工解除隔离不会把状态直接改成正常，也不会启用手工停用的账号/模型。

保存规则会清除此前的自动隔离并重新累计判断；人工隔离保留。规则采用 revision 校验，旧页面不能覆盖其他页面已保存的设置。

网关原有的账号限流、授权、模型白名单及手工停用约束继续生效，解除可用性隔离不会解除这些约束。

## 分发联动

发布选择保持原值。可用性管理另行过滤参与调度的账号；某条路由所有符合模型范围的启用账号都被隔离时，从公共模型目录暂时隐藏。直接调用返回暂不可用 503；同一路由还有其他可用账号时继续提供服务。组合模型仍有未暂停成员时保留。

供应商页面增加可用性入口；下游分发仍显示手工选择，并标注全部候选渠道暂停的原因。未发布模型的下游访问限制不受此功能影响。

## 存储与验证

后端使用现有 SQLite `kv`，作用域 `modelAvailability`，无需数据库结构迁移。服务重启保留状态。请求 ID 的去重窗口为最近 5000 次已记录请求，处理记录保留最近 500 条。

前端：`npm.cmd test`、`npm.cmd run build`。

浏览器：`PREVIEW_URL` 指向真实前端后运行 `node tests/model-availability-live-browser.mjs`。读取真实数据，控制操作在浏览器拦截，不触发模型调用。

后端：`model-availability-service.test.js` 使用隔离存储；`model-availability-routing.test.js` 使用临时 SQLite 和本地 HTTP 假上游，验证实际调度与请求记录，不连接中转站。

被动模式发布：`TENROUTER_PASSIVE_TESTS=1 REEXEC_GUARD=1 bash deploy.sh deploy`。回归保留普通用例的失败、缺失和跳过检查，只排除明确列出的实时调用用例，网络限制阻止测试连接外部服务或本机网关/出口代理；不修改正常回归基线。
