# 模型检测与可用性整合方案

实施日期：2026-10-22。页面整合与手动测试模式已完成开发和回归，尚未部署，生产配置保持原值。

## 已核实的现状

- 前端 `/dashboard/monitor` 包含模型测活、智商、指纹检测，以及模型状态、检测记录、自动检测配置。`MonitorPage.jsx` 已提供单次测试弹窗。
- `/dashboard/availability` 包含业务请求观察、账号/模型渠道状态、隔离控制、自动处理规则和处理记录。
- 已核对线上 `/home/meet/10router` 的实际源码：`POST /api/models/test` 支持 `monitorTarget` 并保存手动检测历史；线上版本自动选择供应商账号。本次暂存实现为 `runManualMonitorTest` 和 `probeTarget` 增加指定渠道账号能力。
- 当前模型测活走供应商执行器，不要求模型已发布给下游。账号连接测试与模型推理测试的含义不同，不能相互替代。
- 当前可用性观察排除内部检测请求，手动测试不属于真实业务证据。可用性默认仅观察。

左侧只保留「模型检测」，主入口沿用 `/dashboard/monitor`，页面统一标题。

| 一级标签 | 二级视图 | 内容 |
| --- | --- | --- |
| 可用性监控 | 渠道状态 / 自动处理规则 / 处理记录 | 保留现有可用性全部能力；渠道行增加单次测试入口和最近手动测试结果 |
| 检测工具 | 模型状态 / 检测记录 / 检测配置 | 保留现有测活、智商、指纹、题库、思考强度、计划、退避和结果详情 |

新默认落在「可用性监控 → 渠道状态」。检测工具保留原来的检测类型切换，不把智商或指纹压缩成可用性指标。

标签和筛选写入 URL，支持刷新与分享定位。旧 `/dashboard/availability` 导航重定向到统一页面的可用性标签，并保留 provider、connectionId、model 筛选；渠道搜索和状态、检测工具搜索、供应商、模型范围、指纹收录/测试/发布状态筛选均保留在 URL。供应商和下游分发的跳转同步调整。这里只保留旧网页链接跳转，不新增后端别名接口。

视觉上共用一个页头、一级标签和当前视图摘要；切换标签只挂载对应工作区，避免出现双页头或同时轮询两个工作区。渠道表分别展示「业务观察」「最近手动测试」「调度状态」，不把三个含义压成一个绿灯。小屏将操作折叠到详情中，保留关键状态与测试入口。

## 手动测试模式

检测权限与可用性自动处理采用两个独立设置。允许测试不等于允许自动隔离，开启自动隔离也不意味着后台可以探测。

| 中转站检测模式 | 真实业务观察 | 点击测试 | 后台定时检测 |
| --- | --- | --- | --- |
| 仅业务观察 | 开启 | 禁止 | 禁止 |
| 手动测试 | 开启 | 允许 | 禁止 |
| 允许定时检测 | 开启 | 允许 | 还需原计划开关、模型选择及账号排除规则允许 |

该权限同时约束主动测活、智商和指纹调用。供应商页面的模型测试入口也检查同一权限；限制必须在服务端落实，不能仅隐藏按钮。实施前梳理所有主动检测入口，包括指纹所用推理路径的内部来源标记，确保不漏掉绕过路径。供应商连接测试应标明是目录/认证测试，并纳入对应站点的主动检查限制。

新站点默认「仅业务观察」。已有检测计划和历史不删除；旧站点未设置模式时展示「待确认」，不推断它已经允许主动检测，执行时按仅业务观察处理。页面列出因此暂停执行的旧计划，用户可按站点改为手动或允许定时；保存前预览影响，不静默修改生产配置。模式切换立即约束后续请求；已经发出的请求可能仍完成并计费。

第一期只增加单个模型渠道的按需测试，不新增批量扫描或自动补测。

## 单次测试流程

1. 用户从某条渠道进入测试，明确显示中转站、账号、模型、请求数量和计费提示；仅打开弹窗不发送请求。
2. 复用并扩展 `POST /api/models/test`，传递明确的 `provider + connectionId + model`。后端验证登录管理权限、检测模式、账号归属和模型范围。
3. 锁定该账号执行一次模型推理，不轮换账号、不切换模型、不自动重试。账号不可用时返回明确原因，不能测试另一个账号后将结果写回原渠道。
4. 返回实际使用的账号、模型、HTTP 状态、耗时、有效回复判定和脱敏错误；保存为手动检测记录。HTTP 200 但空回复不能显示测试通过。
5. 显示最近手动测试时间和结果，同时保留业务观察状态；成功后不自动解除隔离、启用模型或改变发布选择，失败也不进入业务连续失败计数。

已隔离渠道的诊断需明确说明仍处于隔离中。诊断执行仅对指定渠道的这一次请求绕过本模块隔离，不修改持久状态、不开放业务调度；手工停用、账号授权和其他限流约束仍然生效。测试通过后，用户可另行点击现有「解除隔离」。

智商和指纹继续保留自己的请求数量、评分和详情。指纹当前依赖已发布路由，第一期保留此条件并明确展示，不顺带扩大其访问范围。

## 改动范围与实施顺序

1. 前端组合现有两个工作区，去掉独立导航，增加 URL 标签与旧链接跳转；不重写原检测算法。
2. 后端为现有检测配置增加每站点检测模式，调度器、手动测试与指纹入口使用同一权限判定；原计划配置和历史仍用现有存储。
3. 扩展现有手动测试执行器以锁定账号，保存实际账号和来源；可用性界面读取对应的最近手动记录，不把记录喂给业务观察规则。
4. 完成离线回归与真实页面只读验收，核对配置迁移预览后再发布。

不增加依赖，不另建一套探测调度器，不修改原发布白名单或账号启停状态。

## 验收标准

- 原模型测活、智商、指纹、历史、题库、思考强度及计划配置仍可进入和使用；旧链接带筛选正确跳转。
- 仅业务观察站点：手动、定时和其他主动检测入口均被后端拒绝；浏览、筛选、刷新产生的模型推理请求数为零。
- 手动模式：定时任务不调用上游；用户明确执行一次后，只对指定账号和模型发起一次推理。失败不换账号、不重试。
- 允许定时的站点仍遵守原计划、选定模型及排除账号配置；变更模式后不会继续发出后续计划请求。
- 手动结果显示实际账号，不污染业务成功率、失败计数或自动隔离决策；测试成功不解除隔离，不改变模型发布选择。
- 账号归属错误、权限不足、旧版本配置覆盖、重复点击和空回复均有对应验证；重复点击不会产生并发重复测试。
- 运行前后端相关测试及构建；本地假上游验证推理与调度，真实网关用只读浏览器验收和拦截测试写请求，不向禁止检测的中转站发送测试请求。
- 后续若需一次真实上游手动测试，先明确一个允许测试的中转站及账号，再执行；本轮研究不发送模型请求、不调整生产设置。
