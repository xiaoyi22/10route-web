# 供应商新增模型测试评估

本轮仅评估，未修改业务代码、发布服务或发起真实推理。

## 已确认的问题

- `ModelsPage` 的模型行只有复制、编辑、启停和删除，没有测试按钮；真实供应商页面实测模型测试按钮数量为0。
- `ModelEditor` 保存自定义模型后刷新并关闭，未验证模型调用。
- 模型的“已接入”由供应商账号配置推导，不能表示某个新增模型已经调用成功。
- 供应商账号测试发送空对象，未指定新增模型。部分供应商只检查身份或 Token，也不能作为模型可用性的证据。

真实网关页面与登录均为HTTP 200。已登录请求 `POST /api/models/test`，空对象得到400及 `Model required`，确认该路由可达；没有发送模型名称，因此没有产生推理请求。

## 建议实施范围

1. 模型每行增加“测试”；新增模型弹窗保留“保存模型”，增加“保存并测试”。保存成功后使用已保存模型的完整路由 ID 发起测试。
2. 复用 `POST /api/models/test`，传入 `{model: 完整路由ID, kind: 模型类型}`。模型 ID 使用现有目录计算结果，包含供应商实际前缀，避免仅用上游 ID 路由到其他供应商。首轮覆盖当前新增表单支持的文本模型。
3. 独立显示本次测试状态：未测试、测试中、调用成功、调用失败。保留供应商接入及模型启停含义，不能把“已接入”标成“测试通过”。
4. 结果显示被测试的路由 ID、耗时、测试时间、HTTP状态及错误原因；HTTP 200 时仍检查返回体 `ok`，失败可手动重试。后端返回的推理预算耗尽等说明应展示给用户。

测试仅由点击触发，发送真实模型调用，不安排后台自动批量探测。显示的测试结果明确为本次记录，刷新后不能把未保存的旧结果当成持续可用。

## 接口选择与边界

`/api/models/test` 经过实际网关路由，适合验证新增模型是否能通过当前网关调用；同供应商多账号可能由网关选择账号，因此结果应标明“按网关路由测试”。

`/api/providers/[id]/test` 虽接受 `model`，但会更新账号测试状态，部分 OAuth 检查仅验证身份，并不能统一保证执行指定模型推理。`/api/providers/[id]/test-models` 的账号 ID 也仅用于获取供应商及目录，实际调用仍经过网关路由。需要精确指定账号时，应另外设计并核验相应后端能力。

现有 `/api/models/test` 返回耗时和状态，没有返回模型回复及上游实际模型标识。本轮建议先交付调用可用性；需要核对模型替换时，再补充返回字段和对应展示。

## 验收标准

- 新增模型保存后可从行按钮或“保存并测试”完成一次真实调用。
- 请求中供应商前缀和上游模型 ID 与新增记录一致，不能偷偷改成默认模型。
- 成功、无效模型、权限不足、限流、代理故障、超时及HTTP 200业务失败均显示真实结果。
- 测试结果不直接覆盖整个账号的健康状态；无账号和停用模型给出明确提示。
- 回归 `npm.cmd test`、`npm.cmd run build`，在真实网关验证页面和单次模型调用，检查控制台及手机布局。

主要改动预计位于 `src/pages/CorePages.jsx` 和 `src/components/ModelEditor.jsx`，复用现有请求和错误展示组件。第一阶段无需新增后端路由或依赖。
